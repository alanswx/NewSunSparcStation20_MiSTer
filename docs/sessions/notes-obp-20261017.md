## Task 2: NeXTSTEP under OBP

### Sim set-up

`sim/run-obp.sh`'s pieces, by hand (a wrapper in the session scratchpad):
`Vsim_top --rom ss20-obp225.rom --nvram <copy of scratch/nvr/ss20-obp-ttya.nvr>
--ram 64 --hd0 scratch/images/ns33-dl/NeXTSTEP3-3-SPARC_Sun_FIrmware.img --ro
--send 'boot: =>-v\r' --mark 'Starting NEXTSTEP' --mark 'NeXT Mach'
--stop 'NeXT Mach 3.3' --cycles 5G --progress`.

New sim-only aids (this branch):
- `--mark STR` (sim_main.cpp): prints the cycle each time the console prints
  STR; a `--send` that fires prints its cycle too.
- `+pcsample=N [+pcsample_from=C]` (iu.sv): every N cycles each IU prints
  its last committed PC with S/ET/PIL (`pcs` lines, `%m` names the CPU).
- `+iolog_from=C` (ss20_iobridge.sv): `+iolog` from cycle C on; io lines now
  carry the cycle.
- ctrace lines (`+ctrace_from/to`) end with `%m`, so two CPUs' lines can be
  told apart.

### Kernel facts (scratch/ns/mk.elf, kernel.syms)

- `entry` (0xf0002040) saves the romvec (%o0) at 0xf0002030 (`_romp`),
  copies the PROM's trap-table entries for tt 0x1e (level-14 interrupt) and
  tt 0xff into its own table, then `module_setup`, `sparc_init`,
  `setup_main`.
- `startup` calls `kminit`, `kmpopup`, `startup_early`, `panic_init`, then
  `printf(version)` ("NeXT Mach 3.3: ..."): the banner OBP never shows.
- Early console: `cnputc` -> `kmputc`; with no km object, a per-device
  putc; `prom_mayput` uses romvec v2 `write(*fd_stdout, &c, 1)` (romvec
  +0x94, +0xb8) when the romvec version is non-zero, else `nbputchar`
  (+0x5c).

### Finding: the root cause (sim, 1 CPU, reproduces the board exactly)

Sim runs (logs in the worktree's `sim/out/`, not in git): `ns-obp-1cpu`
(plain), `ns-obp-1dbg` (`+pcsample=20000 +iolog` from 800M), `ns-obp-1ct`
(ctrace 802.40M-802.95M), `ns-obp-1ct2` (ctrace in the stuck loop),
`ns-obp-tmr` (every counter/timer access of the whole boot). The run is
deterministic: "Starting NEXTSTEP" at cycle 802,484,881 every time
(1 CPU, `--ram 64`).

1. " ^H" is the **loader's** last output, not the kernel's. Then the
   loader calls romvec+0xa0 (v2 `dumb_mem_free`, by the NetBSD/Linux
   `promvec` layout) with (0xf0180000, 0x3ee000); OBP runs `op-free` ->
   `free-virtual` page by page (the Forth words named from the private
   dictionary listing via W at NEXT), ~2.3M cycles, and returns; the
   loader jumps to the kernel.
2. The kernel runs `sparc_init` (`map_wellknown_devices`, `prom_*`,
   `pmap_bootstrap`, `copy_page_tables`, `probe_pte_0`, ...) and from cycle
   ~850M sits in `_usec_delay` (0xf00964fc/500) at PIL 15 for good (to the
   end of the run at 1.3G, and on the board for 10 min).
3. Counter/timer IO (`+iolog`): at 838.46M the kernel reads processor 0's
   counter (+4, counting), then `set_clk_mode`: reads config (0) and the
   four limits, writes **config = 0xF** (all processor counters User
   Timers), then per CPU +4 = 0, +0 = 0x42900000. From then on processor
   0's +4 reads 0 at every read. `setcpudelay` calibrates `cpudelay`
   (0xf011356c) by doubling it until `us_spin(50)` spans 51200 in that
   count ([*(0xf01380a8)+4]); with a frozen count it doubles for ever.
   The delay loop itself executes correctly (ctrace: o3 counts down, o0
   advances).
4. The count is frozen because processor 0's User Timer **RUN** bit is 0.
   `ns-obp-tmr`: OBP's `reset_power_on` writes +0xC = 0, config = 1,
   MSW/LSW = 0, **+0xC = 1** (cycle 43,320), polls the user timer for its
   keyboard time-out until 111M; then `obp_prep` issues SW_RST (README of
   the OBP notes, 3.2/obp_prep), the machine comes back through
   `obp_start`, and from 180M OBP writes counter-mode limits with no
   config write: the software reset had put the timer block, RUN included,
   back to its reset state. OBP never writes +0xC again (to 840M).
5. Under OpenBIOS the same kernel works because OpenBIOS's
   `ob_counter_init` writes `cpu_timers[0].cntrl = 1` (RUN) and there is
   no software reset. QEMU's slavio_timer resets RUN to 1 on every reset.
   The NCR89C105 text says RUN clears on reset, the Sun-4M spec (§5.3.4,
   §12: "Counter/Timers: Initialized") gives no value. NeXTSTEP 3.3 booted
   under this OBP on the VHDL core (and is a shipping SS20 OS), so RUN
   must survive SW_RST on the real machine.

Not the cause (checked): the second CPU (1-CPU sim identical), the PROM's
putchar path, the loader's PROM calls, the MMU take-over.

### Fix (28949d1)

`slavio_timer` gets `swr_i` (with `rst`: the reset is the software
reset); RUN is cleared only by a power-on reset, everything else resets as
before. `ss20_machine` passes `rst_swr`; `sim/cpu/cpu_sim.sv` ties it to 0.
`tb_slavio_timer`: the OBP-then-kernel sequence (RUN=1 in user mode,
SW_RST, config/limit reset but RUN kept, OBP's L14 limit, config 0xF,
LSW/MSW written, the count advances without a RUN write; processor 1's
RUN stays 0; a power-on reset clears RUN): PASS, 146 checks, lint clean.

Sim with the fix (`--ro` disk): 1 CPU `ns-obp-1fix`: "NeXT Mach 3.3"
banner at 851.8M (49M cycles after "Starting NEXTSTEP"), then the drivers,
en0, sc0, sd0, sd1, kmDevice0, "root on sd0", and a panic "Root device is
physically write protected" (expected: `--ro`). 2 CPUs `ns-obp-2fix`:
banner at 908.8M (49.7M after "Starting NEXTSTEP" at 859.1M).

Quartus (misterubuntu `~/mister/ss20-obp`): seed 1 fits at 39,271 ALMs
(94 %) but clk_sys misses at -0.784 ns (TNS -1.803), as the board core's
seed 1 did (-0.731): not board-worthy (md5 5fd7b7e8). Seed 4 queued.
